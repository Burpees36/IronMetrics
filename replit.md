# Iron Metrics — Gym Management SaaS

## Overview

Iron Metrics is a full production-grade gym management SaaS platform designed for CrossFit and functional fitness gyms. It provides comprehensive tools for gym operations, including member management, billing, scheduling, programming, lead management, and an AI-powered assistant. The platform aims to streamline administrative tasks, enhance member engagement, and provide actionable intelligence for gym owners.

## System Architecture

Iron Metrics is built as a pnpm workspace monorepo using TypeScript.

**Monorepo Structure:**
- `artifacts/api-server/`: Express 5 API server.
- `artifacts/iron-metrics/`: React + Vite frontend.
- `artifacts/mockup-sandbox/`: Design prototyping sandbox (not part of sellable product).
- `lib/`: Shared libraries including OpenAPI spec, generated API clients, Drizzle ORM schema, and Replit Auth hooks.

**Audit Reference:** `.local/tier1-beta-audit.md` — current source of truth for Tier 1 beta readiness assessment. The old `IRON_METRICS_ANALYSIS.md` has been removed as stale.

**Technology Stack:**
- **Node.js:** 24, with pnpm as the package manager.
- **TypeScript:** 5.9.
- **API:** Express 5.
- **Frontend:** React, Vite, TailwindCSS v4, shadcn/ui.
- **Database:** PostgreSQL with Drizzle ORM.
- **Validation:** Zod (`zod/v4`).
- **API Codegen:** Orval (from OpenAPI spec).
- **Auth:** Replit Auth (OIDC with PKCE).
- **UI/UX Design:** Premium SaaS theme with light/dark mode toggle. Dark mode uses `hsl(224 35% 6%)` background, `hsl(224 35% 9%)` cards; light mode uses `hsl(210 20% 98%)` background with white cards. Both modes use 2xl rounded corners and a glass-panel effect. Primary accent is amber/gold. Theme is managed by `ThemeProvider` context (`src/store/ThemeContext.tsx`), persisted to `localStorage` key `iron-metrics-theme`, and respects `prefers-color-scheme` on first visit. An inline script in `index.html` prevents flash on load. Toggle is in the landing page navbar (desktop + mobile) and the authenticated sidebar.

**Key Features & Implementation:**

- **Subscription Tiers & Feature Gating:** Three tiers (Insights $99/mo, Growth $199/mo, Pro $299/mo) with beta access flag. Tier config is the single source of truth in `artifacts/api-server/src/tierConfig.ts`. Backend middleware `requireTierAccess` gates gated routes. Frontend uses `useGymTier` hook and `TierGate` component to show `UpgradePrompt` on locked pages. Sidebar nav items show a lock icon for locked routes. Three Stripe Products and Prices are created automatically on server startup (`platformStripeService.ts`). Platform subscription management via `/api/gyms/:gymId/platform-billing/*` endpoints. Stripe Checkout + Billing Portal for subscription management. Webhook handlers for `customer.subscription.*` events update the gym's `subscriptionTier` field. `isBetaAccess` flag grants free Pro access (toggled via `/api/admin/gyms/:gymId/beta-access` with `PLATFORM_OWNER_SECRET` header). Cancellation sets `platformCancelAtPeriodEnd` and downgrades at period end via webhook.
- **DB fields added to gyms:** `subscriptionTier` (default: "none"), `isBetaAccess` (boolean), `stripeGymCustomerId`, `platformSubscriptionId`, `platformCancelAtPeriodEnd`, `platformCurrentPeriodEnd`.
- **Multi-tenancy:** `gyms` table for isolated workspaces.
- **Member Management:** Full CRM, risk scoring, notes, lifecycle events, and CSV/Wodify import with sync run tracking. Import dialog offers source selection: Wodify (auto-detects format, deduplicates multi-membership members by Client ID + email, consolidates revenue across plans, handles both date formats and scientific notation amounts, tags email opt-outs, shows MRR and membership breakdown preview) or Generic CSV (manual column mapping). Backend: `POST /api/gyms/:gymId/members/import/preview`, `POST .../import/confirm`, `POST .../import/wodify/preview` with 5k row limit. Every import creates a `sync_runs` record tracking status (running/completed/completed_with_errors/failed), row counts, error details, and timestamps. Sync history: `GET /api/gyms/:gymId/sync-runs` (list), `GET .../sync-runs/latest`. Frontend: `ImportMembersDialog.tsx` with source → upload → preview → import flow, `SyncStatusBanner.tsx` on Members page showing latest import status + expandable history with retry action. Schema: `sync_runs` table (gymId, source, status, fileName, totalRows, created, skipped, errored, errorDetails JSONB, startedAt, completedAt, triggeredBy). Designed for future scheduled sync extension.
- **Wodify API Sync Engine:** Live-verified integration with Wodify API (api.wodify.com/v1). Syncs clients and memberships via API key authentication. DB schema: `wodify_client_id` (integer, nullable) + `monthly_revenue` (numeric) + `total_class_sign_ins` (integer) + `current_weekstreak` (integer) on members table; `wodify_api_key` (text, nullable) on gyms table; index on (gym_id, wodify_client_id). API client handles pagination (100/page) with page-level progress callbacks, sentinel date filtering (1900-01-01), and error handling. Client normalization maps Wodify fields to Iron Metrics schema with phone normalization, status mapping, tag merging (email/sms opt-out), and emergency contacts. Membership consolidation computes MRR per member with interval normalization (weekly/monthly/quarterly/annual → monthly). Dedup strategy: match by wodifyClientId first, then by email (only if no existing wodifyClientId on the email match — prevents overwriting). **Async sync pattern:** POST /sync returns immediately with `{ syncRunId, status: "running" }`. Sync runs in background, updating `metadata.progress` JSONB on the sync_runs record after each phase (fetching-clients, fetching-memberships, processing, writing, complete/failed). Progress includes: phase, currentPage, totalItemsFetched, processed/totalToProcess, created/updated counts, and human-readable message. Frontend polls GET sync-status every 2s via `useWodifySyncPolling` hook. Hook handles: auto-detection of running syncs on mount, elapsed time tracking, 409 (already running) by attaching to existing sync, and interval dedup guards. API endpoints: `POST /api/gyms/:gymId/integrations/wodify/validate-key` (validates key + stores on gym), `POST .../wodify/sync` (triggers async sync, returns syncRunId), `GET .../wodify/sync-status` (latest sync runs + progress + maskedKey). Files: `artifacts/api-server/src/routes/integrations/wodify/{client,sync,index,types}.ts`, `artifacts/iron-metrics/src/hooks/useWodifySyncPolling.ts`. **Frontend UI:** WodifyConnectionCard in Settings → Integrations with full lifecycle (disconnected → entering-key → validating → validated → syncing → sync-complete → connected). Syncing state shows animated progress bar with phase messages, elapsed time, and member count. Connected state shows masked API key (last 4 chars), last sync info. Re-sync requires confirmation dialog; disconnect requires confirmation with warning. Error state shows retry button. ImportMembersDialog and Onboarding MembersStep both use the same polling hook for consistent async progress UI. Timeout warning after 2 minutes lets user know sync continues in background.
- **Lead Management:** Kanban-style pipeline with activity timelines, follow-up scheduling, and conversion flows. Public lead capture form at `/join/:gymSlug` (no auth required) with configurable source label, case-insensitive gym-scoped dedup, and activity logging. Lead Capture Form Management admin UI with config for headline/subheadline/CTA text, field visibility (phone, interests, consent), attribution (source label, campaign tag, default stage), and analytics dashboard. Config stored in `lead_capture_config` table (one per gym). Rate limited at 20 req/15min.

- **Billing:** Comprehensive billing command center with plans, subscriptions, payments, refunds, and full Stripe integration. Billing audit logs and webhook idempotency are implemented. Grace period enforcement (14-day default) escalates to `grace_expired` status with final warning email. Maintenance endpoint handles token cleanup (30-day expired), recovery archival (90-day resolved), and grace evaluation. Public payment-update endpoints have dedicated rate limiting (15 req/15min) and structured security logging. Recovery endpoints are fully documented in the OpenAPI spec. **Card Management:** Full payment method management on MemberDetail billing tab — add card (SetupIntent), set default, remove card with confirmation. Each card shows brand/last4/expiry + DEFAULT badge. Backend: `POST set-default`, `DELETE` payment method endpoints in billing routes, `setDefaultPaymentMethod` and `detachPaymentMethod` in stripeService. **Couples/Linked Billing:** `linkedBillingMemberId` column on members table links one member's billing to another (primary payer). Backend: `POST link-billing`, `POST unlink-billing`, `GET linked-billing` endpoints in members routes with timeline event logging. Frontend: Couples Billing card on MemberDetail billing tab with Link Partner dialog (search + select), unlink button, primary/dependent status indicators. **Plan Upgrade/Downgrade:** `changePlan` and `previewPlanChange` in stripeService. Supports immediate (with proration) and next-cycle timing. Frontend: ChangePlanDialog component on MemberDetail with plan selection, proration preview, timing choice. **Scheduled Holds:** `scheduled_holds` table tracks hold lifecycle (scheduled → active → completed/cancelled). Routes: create/edit/cancel holds, auto-processing in billing-maintenance scheduler activates holds on startDate and ends on endDate, pauses/resumes Stripe subscriptions. Frontend: HoldsManager component with hold scheduling, cancel, and past hold history. **Past-Due Check-In Enforcement:** `checkin-status` route checks holds + past-due recovery state + gym `pastDuePolicy` (allow/grace_period/strict). **Discount Codes:** `discount_codes` table + Stripe Coupon integration. CRUD routes, apply/remove from subscriptions. Frontend: DiscountManager component on Billing page with code creation, toggle active/inactive, usage tracking. **Account Credits:** `getMemberBalance` and `adjustMemberBalance` in stripeService using Stripe customer balance. Frontend: MemberBalance component with add/deduct credit dialog. **Invoice/Receipt Access:** `getMemberStripeInvoices` route fetches invoices from Stripe with hosted_invoice_url and invoice_pdf links. Frontend: InvoiceTable component on MemberDetail. **Tax Configuration:** `tax-config` routes + `createOrUpdateTaxRate` in stripeService using Stripe Tax Rates. Gym columns: `taxEnabled`, `taxLabel`, `taxRate`, `taxJurisdiction`, `stripeTaxRateId`. Frontend: TaxSettings component on Billing Settings tab.

## Wodify Integration
- **Field Map:** `docs/integrations/wodify-field-map.ts` — source-of-truth mapping between Wodify API/CSV entities and Iron Metrics schema. LIVE-VERIFIED 2026-03-25 against api.wodify.com/v1.
- **Integration Types:** `artifacts/api-server/src/routes/integrations/wodify/types.ts` — TypeScript interfaces for verified Wodify API response shapes (WodifyClient, WodifyMembership, WodifyClass, WodifyProgram, WodifyLead) and normalized Iron Metrics forms.
- **API Probe:** `artifacts/api-server/src/routes/integrations/wodify/probe.ts` — one-time endpoint discovery script.
- **Available Endpoints:** GET /clients (73 fields), GET /memberships (50 fields), GET /classes (69 fields), GET /programs (12 fields), GET /leads (47 fields). Pagination: ?page=N, 100/page.
- **Unavailable:** /invoices, /attendance, /class-signins, /reservations, /client-statuses, /revenue-categories (all 403).
- **Tier 1 Data Gap SOLVED:** /clients includes attendance summary: last_attendance, days_since_last_attendance, total_class_sign_ins, is_at_risk, current_weekstreak. No dedicated attendance endpoint needed for Tier 1 risk scores.
- **Sync Order:** Clients → Memberships → Programs (optional) → Classes (Growth) → Leads (Growth).
- **MRR Calculation:** membership.payment_plan.renewal_payment_option.renewal_cost (for auto-renew) or initial_payment_option.initial_cost. Interval from initial_payment_interval_time_unit/length.
- **Schema Changes Needed:** `wodify_client_id` column on members, `wodify_api_key` on gyms, 'wodify-api' as sync_runs source.
- **Observed Client Statuses:** 'Active', 'Inactive'. Date sentinel: '1900-01-01' = null/not-set.
- **Remaining Questions:** Date range filtering params, rate limits (none observed).
