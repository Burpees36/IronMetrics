# Iron Metrics — Gym Management SaaS

## Overview

Iron Metrics is a full production-grade gym management SaaS platform designed for CrossFit and functional fitness gyms. It provides comprehensive tools for gym operations, including member management, billing, scheduling, programming, lead management, and an AI-powered assistant. The platform aims to streamline administrative tasks, enhance member engagement, and provide actionable intelligence for gym owners, enabling them to optimize operations and improve member retention.

## System Architecture

Iron Metrics is built as a pnpm workspace monorepo using TypeScript, adhering to a structured architecture for scalability and maintainability.

**Monorepo Structure:**
- `artifacts/api-server/`: Express 5 API server.
- `artifacts/iron-metrics/`: React + Vite frontend.
- `lib/`: Shared libraries including OpenAPI spec, generated API clients, Drizzle ORM schema, and Replit Auth hooks.

**Technology Stack:**
- **Node.js:** 24, with pnpm.
- **TypeScript:** 5.9.
- **API:** Express 5.
- **Frontend:** React, Vite, TailwindCSS v4, shadcn/ui.
- **Database:** PostgreSQL with Drizzle ORM.
- **Validation:** Zod (`zod/v4`).
- **API Codegen:** Orval (from OpenAPI spec).
- **Auth:** Replit Auth (OIDC with PKCE).

**UI/UX Design:**
A premium SaaS theme with light/dark mode toggle, 2xl rounded corners, and a glass-panel effect. The primary accent is emerald green, with violet for the Pro tier. Amber/yellow is reserved for warnings. Theme management uses `ThemeProvider` context, persisted to `localStorage`, and respects `prefers-color-scheme`.

- **Subscription Tiers & Feature Gating:** Three tiers (Insights $99/mo, Growth $199/mo, Pro $299/mo) with beta access flag. Tier config is the single source of truth in `artifacts/api-server/src/tierConfig.ts`. Backend middleware `requireTierAccess` gates gated routes. Frontend uses `useGymTier` hook and `TierGate` component to show `UpgradePrompt` on locked pages. Sidebar nav items show a lock icon for locked routes. Three Stripe Products and Prices are created automatically on server startup (`platformStripeService.ts`). Platform subscription management via `/api/gyms/:gymId/platform-billing/*` endpoints. Stripe Checkout + Billing Portal for subscription management. Webhook handlers for `customer.subscription.*` events update the gym's `subscriptionTier` field. `isBetaAccess` flag grants free Pro access (toggled via `/api/admin/gyms/:gymId/beta-access` with `PLATFORM_OWNER_SECRET` header). Cancellation sets `platformCancelAtPeriodEnd` and downgrades at period end via webhook.
- **DB fields added to gyms:** `subscriptionTier` (default: "none"), `isBetaAccess` (boolean), `stripeGymCustomerId`, `platformSubscriptionId`, `platformCancelAtPeriodEnd`, `platformCurrentPeriodEnd`.
- **Multi-tenancy:** `gyms` table for isolated workspaces.
- **Member Management:** Full CRM, risk scoring, notes, lifecycle events, and CSV/Wodify import with sync run tracking. Import dialog offers source selection: Wodify (auto-detects format, deduplicates multi-membership members by Client ID + email, consolidates revenue across plans, handles both date formats and scientific notation amounts, tags email opt-outs, shows MRR and membership breakdown preview) or Generic CSV (manual column mapping). Backend: `POST /api/gyms/:gymId/members/import/preview`, `POST .../import/confirm`, `POST .../import/wodify/preview` with 5k row limit. Every import creates a `sync_runs` record tracking status (running/completed/completed_with_errors/failed), row counts, error details, and timestamps. Sync history: `GET /api/gyms/:gymId/sync-runs` (list), `GET .../sync-runs/latest`. Frontend: `ImportMembersDialog.tsx` with source → upload → preview → import flow, `SyncStatusBanner.tsx` on Members page showing latest import status + expandable history with retry action. Schema: `sync_runs` table (gymId, source, status, fileName, totalRows, created, skipped, errored, errorDetails JSONB, startedAt, completedAt, triggeredBy). Designed for future scheduled sync extension.
- **Wodify API Sync Engine:** Live-verified integration with Wodify API (api.wodify.com/v1). Syncs clients and memberships via API key authentication. DB schema: `wodify_client_id` (integer, nullable) + `monthly_revenue` (numeric) + `total_class_sign_ins` (integer) + `current_weekstreak` (integer) on members table; `wodify_api_key` (text, nullable) on gyms table; index on (gym_id, wodify_client_id). API client handles pagination (100/page) with page-level progress callbacks, sentinel date filtering (1900-01-01), and error handling. Client normalization maps Wodify fields to Iron Metrics schema with phone normalization, status mapping, tag merging (email/sms opt-out), and emergency contacts. Membership consolidation computes MRR per member with interval normalization (weekly/monthly/quarterly/annual → monthly). Dedup strategy: match by wodifyClientId first, then by email (only if no existing wodifyClientId on the email match — prevents overwriting). **Async sync pattern:** POST /sync returns immediately with `{ syncRunId, status: "running" }`. Sync runs in background, updating `metadata.progress` JSONB on the sync_runs record after each phase (fetching-clients, fetching-memberships, processing, writing, complete/failed). Progress includes: phase, currentPage, totalItemsFetched, processed/totalToProcess, created/updated counts, and human-readable message. Frontend polls GET sync-status every 2s via `useWodifySyncPolling` hook. Hook handles: auto-detection of running syncs on mount, elapsed time tracking, 409 (already running) by attaching to existing sync, and interval dedup guards. API endpoints: `POST /api/gyms/:gymId/integrations/wodify/validate-key` (validates key + stores on gym), `POST .../wodify/sync` (triggers async sync, returns syncRunId), `GET .../wodify/sync-status` (latest sync runs + progress + maskedKey). Files: `artifacts/api-server/src/routes/integrations/wodify/{client,sync,index,types}.ts`, `artifacts/iron-metrics/src/hooks/useWodifySyncPolling.ts`. **Frontend UI:** WodifyConnectionCard in Settings → Integrations with full lifecycle (disconnected → entering-key → validating → validated → syncing → sync-complete → connected). Syncing state shows animated progress bar with phase messages, elapsed time, and member count. Connected state shows masked API key (last 4 chars), last sync info. Re-sync requires confirmation dialog; disconnect requires confirmation with warning. Error state shows retry button. ImportMembersDialog and Onboarding MembersStep both use the same polling hook for consistent async progress UI. Timeout warning after 2 minutes lets user know sync continues in background.

ARM = blended MRR / active billable members. Engagement rate blends attendance table records with Wodify summary fields (lastVisitDate, daysSinceLastAttendance). Risk profiles use member.monthlyRevenue as fallback for revenue-at-risk when no subscription exists. All API responses include `revenueSource` ('subscriptions_only'|'wodify_only'|'blended'), `attendanceSource`, and `hasSubscriptionData` metadata. Dashboard chart renamed "MRR Trend". - **Error Handling:** React `ErrorBoundary` for graceful UI recovery.
- **Data Integrity:** Drizzle numeric fields are handled as strings and parsed to floats. Backend returns parsed decimal dollars for subscription amounts. PostgreSQL `COUNT(*)` returns bigint (string in JS) — all count results are wrapped with `Number()` across all route files. Tenure calculations fall back to `createdAt` when `joinDate` is NULL. Revenue trend uses subscription MRR for current month when no invoices exist.
- **Database Indexes:** Foreign key columns across all tables have B-tree indexes for query performance (attendance, members, member_notes, timeline_events, leads, lead_activities, workouts, workout_results, programming_days, subscriptions). Composite indexes on common query patterns (e.g., gym+status, gym+date, member+date).
- **Date Columns:** All date-only fields use PostgreSQL `date` type with `mode: "string"` in Drizzle, returning/accepting YYYY-MM-DD strings in the API (joinDate, birthDate, workoutDate, nextFollowUpDate, currentPeriodStart/End, dueDate, programming date).
