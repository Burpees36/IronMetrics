You are a senior SaaS product engineer, UX architect, and security-minded admin systems designer. Upgrade the existing Settings area of this gym operating system into a production-ready Settings + Administration Center for a real gym business.

CURRENT STATE
Right now the Settings page has:
- General tab with read-only gym information
- Email settings inputs
- Staff tab with a static staff table
- Invite Staff button
- Staff rows are not clickable/editable
- No way to update gym basics
- No way to manage roles/permissions properly
- No way to update billing/subscription plan
- No way to manage password/security/account settings
- No polished administrative workflow yet

GOAL
Turn Settings into a complete, production-level administration area that a gym owner can actually use to manage their business, staff access, brand details, email identity, and account-level controls.

This should feel premium, secure, and operationally useful — not like a placeholder admin page.

HIGH-LEVEL PRODUCT DIRECTION
Split Settings into a structured admin experience with clear categories, polished UX, and role-safe controls.

Recommended information architecture:
- General
- Staff & Access
- Billing & Plan
- Notifications / Email
- Security
- Branding
- Integrations
- Member App / Public Settings
- Danger Zone

If needed, use sidebar navigation on desktop and a stacked/tabbed mobile layout.

CORE REQUIREMENTS

1. GENERAL SETTINGS MUST BECOME EDITABLE
Convert the current read-only gym information card into a real editable experience.

Include:
- gym name
- legal/business name if different
- address
- phone
- support/contact email
- timezone
- website
- business description / short summary
- default class/programming terminology if relevant
- save/cancel flow
- dirty state / unsaved changes warning
- validation and friendly error states

UX requirements:
- editable form sections
- inline validation
- success toast after save
- disable save when no changes exist
- loading skeletons where appropriate

2. STAFF & ACCESS MUST BE FULLY MANAGEABLE
The current staff table should become a true staff management center.

Implement:
- clickable staff rows
- staff detail drawer or profile page
- edit staff member name if allowed
- edit role
- activate/deactivate staff access
- resend invite
- revoke invite
- remove staff member from gym
- transfer ownership safeguards
- role descriptions in UI
- permission summaries per role

Support statuses such as:
- invited
- active
- suspended
- removed

Add search/filter/sort if practical:
- search by name/email
- filter by role
- filter by status

IMPORTANT:
Owners should be able to manage access cleanly if a coach leaves, a partner is removed, or responsibilities change.

3. ROLE / PERMISSION SYSTEM
Formalize and surface the access model.

Recommended roles:
- Gym Owner
- Admin / Manager
- Head Coach
- Coach
- Front Desk
- Analyst / Read Only

For each role, define permissions for things like:
- view analytics
- manage staff
- manage programming
- manage members
- manage billing
- manage integrations
- send communications
- edit gym settings

At minimum:
- enforce server-side role checks
- show role permissions in the UI
- prevent unsafe privilege escalation
- require special confirmation for owner-level changes

If custom roles are too much for this sprint, create a strong fixed-role system with a clean foundation for custom permissions later.

4. BILLING & PLAN SETTINGS
Create a dedicated Billing & Plan section even if some parts are placeholders for now.

Include:
- current subscription plan
- plan status
- billing cycle
- next renewal date
- payment method summary placeholder or real integration-ready card
- seats/staff limits if relevant
- upgrade/downgrade/change plan CTA
- billing history/invoices section placeholder if backend is not fully ready
- owner-only visibility and access

Important:
This should be structured in a way that can later connect to Stripe billing/subscription management cleanly.

If live self-serve subscription management is not fully implemented yet:
- still build the UI shell and route structure
- mark unavailable actions gracefully
- do not fake actual billing actions

5. ACCOUNT / PASSWORD / SECURITY
Create a real Security section for the logged-in user and for owners/admins where appropriate.

Include:
For current user:
- change password
- reset password flow entry point if auth provider requires it
- last login if available
- email/login identity display
- session/security messaging

For gym-level admin security:
- who can invite staff
- who can manage billing
- ownership safeguards
- optional 2FA readiness placeholder if not yet implemented
- audit-friendly admin changes where practical

If auth is handled by Supabase/Auth provider, wire the UI correctly to that flow rather than trying to own password logic in an unsafe way.

6. EMAIL / NOTIFICATIONS SETTINGS
The current Email Settings block should be upgraded.

Include:
- from name
- from email
- reply-to email if appropriate
- sender verification status if available
- email preview/example
- explanation of where these settings are used
- test email action if practical
- save state and validation

Also include notification preferences if relevant:
- invite notifications
- billing notifications
- integration alerts
- member communication defaults
- AI/operator outbound communication defaults if part of the platform

7. BRANDING SETTINGS
Add a Branding section.

Include:
- gym logo upload
- favicon/app icon placeholder if relevant
- primary brand color
- accent color
- preview of how branding appears in emails/member-facing surfaces
- fallback if no custom branding is uploaded

This should support future white-label polish.

8. INTEGRATIONS SETTINGS
Add an Integrations section or route.

Include cards/status for:
- Wodify
- Stripe
- Email provider
- SMS provider if relevant
- future integrations placeholder

Each integration card should show:
- connected / not connected / attention needed
- last sync or status text if available
- configure/manage CTA
- disconnect action with confirmation if allowed

9. MEMBER APP / PUBLIC-FACING SETTINGS
Add settings for the member-facing experience where appropriate.

Examples:
- allow members to view programming
- allow result logging
- show leaderboard
- show coach notes to members (likely off)
- member app branding basics
- public gym profile options
- communication preferences defaults

Only include settings that make sense for the current product direction, but create the structure for this to grow.

10. DANGER ZONE
Add a clearly separated Danger Zone at the bottom.

Possible actions:
- archive gym
- deactivate gym
- disconnect an integration
- remove a staff member permanently
- transfer ownership
- delete gym (if not supported, omit destructive implementation but leave architecture ready)

All destructive actions must require:
- confirmation modal
- strong warning copy
- owner-only access
- server-side validation
