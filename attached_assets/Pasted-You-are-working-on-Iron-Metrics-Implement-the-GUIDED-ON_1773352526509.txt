You are working on Iron Metrics. Implement the GUIDED ONBOARDING WIZARD SHELL ONLY.

This sprint happens after Day 2 CSV member import is complete or mostly complete.
Do not build Wodify import, Mindbody import, billing migration, payment failure emails, update card flow, forecasting, retention automations, or member self-service.
Do not overbuild this into a giant setup framework.
Build a premium, production-ready onboarding shell that gets a real gym from signup to usable system state quickly.

OBJECTIVE
Create a step-by-step onboarding experience for new gym owners so they can set up their gym without feeling lost. The wizard should orchestrate setup, reduce confusion, and bridge into the real product.

WHY THIS EXISTS
Iron Metrics already has major building blocks, but onboarding is fragmented. The analysis identified guided setup as required for <30 minute onboarding and specifically listed guided onboarding wizard as a Tier 1 production requirement. This sprint should make setup feel intentional, calm, and premium.

SUCCESS CRITERIA
- A newly created gym owner sees a guided setup flow instead of being dropped into an empty product with no direction.
- The wizard is broken into clear, manageable steps.
- Each step saves progress.
- The wizard can be exited and resumed later.
- Completion of the wizard leaves the gym in a genuinely usable initial state.
- The wizard routes the user into the right next experience after setup.
- The UI feels polished and confidence-building, not cluttered or juvenile.

WIZARD SCOPE
Build the shell around these setup steps:

STEP 1 — Welcome / Gym Basics
- Gym name
- Timezone
- Address/location if supported
- Contact email / phone if those fields exist
- Brand basics if already supported in schema/settings
- Friendly explanation of what setup will do

STEP 2 — Membership Plans
- Show existing plans if already created
- Let the owner add at least one membership plan if none exist
- Lightweight plan creation only using fields the current product already supports
- Do not redesign the billing system here

STEP 3 — Staff / Coaches
- Show existing staff if present
- Allow invite of coaches/admins/owners using existing invite flow if available
- If invite flow already exists, integrate it into onboarding instead of rebuilding it
- If no staff are added, allow continuing with just the owner

STEP 4 — Members
- Bridge into the CSV member import flow from Day 2
- If members already exist, show success state and let the user continue
- If no members yet, give two clear choices:
  - Add one manually
  - Import via CSV
- Do not rebuild import logic here; reuse the Day 2 import flow

STEP 5 — First Schedule Setup
- Help the owner create their first usable week of classes
- For this wizard sprint, keep this lightweight:
  - either add a few starter classes manually
  - or choose a very basic starter weekly structure if available
- Do not build the full template engine in this sprint
- This step is meant to avoid an empty schedule, not solve long-term scheduling

STEP 6 — Finish / Launch
- Show a completion summary:
  - gym created
  - plans configured
  - staff invited
  - members added/imported
  - first classes created
- Provide strong CTA buttons:
  - Go to Dashboard
  - Go to Schedule
  - Go to Members
- Reinforce what the owner should do next

STATE / PROGRESSION REQUIREMENTS
- Track wizard progress per gym and per user where appropriate
- The user must be able to leave and resume later
- Each step should save independently
- Mark steps as complete/incomplete
- Allow going backward without losing data
- Do not require every optional step to be completed to finish
- If data already exists, pre-fill or mark the step as already done

ENTRY RULES
- Show the onboarding wizard automatically for newly created gyms or gyms with minimal setup
- Provide a “Resume Setup” entry point on dashboard/settings for unfinished setups
- Do not trap experienced users in the wizard forever
- Add a way to skip for now, but make it easy to resume

UX REQUIREMENTS
- Premium, calm visual design
- Strong progress indicator
- Clear titles and plain-English descriptions
- No technical jargon
- Warm empty states
- Minimal friction
- Mobile-safe layout, but desktop-first polish
- Use existing design system components and app styling
- Avoid giant forms on one screen

TECHNICAL REQUIREMENTS
- Reuse existing backend endpoints wherever possible
- Add only the minimum new endpoints/state needed to support wizard progress and step completion
- Respect Day 1 gym access protections
- Do not duplicate existing member import, plan creation, or invite logic
- If there is no existing persistent onboarding state, add a simple gym-scoped onboarding progress record or equivalent
- Keep implementation simple and durable

DATA / LOGIC REQUIREMENTS
- Determine “setup completeness” from real system state where possible, not only UI flags
- Example:
  - Gym basics step complete if required gym fields exist
  - Plans step complete if at least one active plan exists
  - Staff step complete if at least one staff member beyond owner exists, or owner explicitly skips
  - Members step complete if at least one member exists
  - Schedule step complete if at least one upcoming class exists
- Use persisted skip/complete states only when necessary for optional steps

OUT OF SCOPE
Do not build:
- Direct third-party imports
- Payment migration
- Tax settings
- Marketing automation
- Full class template engine
- Forecasting
- Morning briefing
- Member portal
- Communication hub
- Billing recovery flows

TESTING / VALIDATION
After implementation, verify:
1. A brand-new gym owner is guided into onboarding instead of landing in a confusing empty state.
2. Progress is saved after each step.
3. The user can leave and resume later.
4. Existing data pre-populates or auto-completes the relevant steps.
5. Members step reuses the CSV import flow cleanly.
6. First-time users can reach a usable initial state without confusion.
7. Finishing the wizard drops the owner into the right place in the app.

DELIVERABLES
Provide:
1. Files changed
2. What was implemented in each file
3. Any schema/config changes
4. Any new onboarding state model added
5. What was intentionally deferred
6. Manual QA checklist

GUARDRAILS
- Build the wizard shell well.
- Reuse existing logic.
- Do not overbuild.
- Do not start template engine or billing recovery in this sprint.
- Focus on making setup feel real, smooth, and trustworthy.
